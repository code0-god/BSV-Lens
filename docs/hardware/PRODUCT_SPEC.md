The [G1-BSV contract](G1_BSV_CONTRACT.md) supersedes a netlist-only default,

contract and all validated G1 artifacts.

Default objects are actual BSV module/storage occurrences and typed
interfaces/method boundaries, linked by evidenced source/compiler relations.
Every BSV label has canonical definition identity, occurrence context, source
range and source revision. Source-derived does not mean guessed netlist wiring.
Source Map and ProtocolChannel/Methods/Endpoints buckets are not the fallback
default architecture.

The default journey is BSV overall; module body click; BSV interior; select
storage/port/relation; inspect its rule/method/expression and original source;
explicitly open RTL Implementation; Back to the previous BSV scene.
Rules/methods are behavior overlays, functions/expressions semantic operations,
not invented physical modules. Storage does not automatically decompose to RTL.

Each semantic line reports relation kind, source statement, compiler
confirmation and whether RTL correspondence exists. Explicit RTL signal
disclosure shows actual metadata-backed RDY/EN/argument/result ports.
The absence of one payload type is not no-payload or control-only.

## Outcome

BSV Lens becomes an analyzer of a **particular compiled hardware build**.
The default BSV architecture identifies its real source and compiler evidence.
RTL Implementation identifies every displayed cell/port/wire in the chosen
artifact. Semantic relations and artifact connectivity have separate truth
contracts; neither is a substitute for the other.

The first delivery stops at G0/G1: audit, real compiler/reader experiments,
separate model contracts, and an executable schematic experiment. It is not
the production renderer replacement. G2-G7 require the user's design approval.
Extension identity remains `code0-god.bsv-lens`; existing command/configuration
namespace remains `bsvArchitecture.*`.

## Two independent acceptance axes

1. **Artifact structure fidelity:** preserve every module definition, occurrence,
   cell, port, ordered connection bit, alias, constant, and unknown object in
   the supported artifact stage. Rendering fewer objects does not reduce the
   canonical model or justify an incomplete importer.
2. **Source correspondence fidelity:** give the actual evidence for each
   hardware-to-RTL-to-BSV relation. Generated RTL evidence is not original BSV
   evidence. Measure verified, partial, ambiguous, and unmapped coverage over
   an explicit complete denominator.

`Structure import verified` never implies `original BSV mapping complete`.
Unknown mapping is an honest result and an unfinished research objective,
not proof that an object is compiler-generated or optimized away.

## User journey and questions

The default journey is:

```text
Choose build
  -> BSV module occurrence hierarchy
  -> click one module body to see BSV children/storage and typed boundaries
  -> select a semantic relation, port or storage
  -> inspect source behavior, conditions and original evidence
  -> explicitly open same-context RTL Implementation when needed
  -> inspect actual cell/port/net/bit evidence
  -> Back restores the previous distinct BSV scene and its viewport
```

The canvas answers:

- What actually exists, where is it contained, and which definition does this
  occurrence instantiate?
- Which ordered bits belong to a port, and which pins share those bits?
- Which driver/load roles are known from the artifact, and which are unknown?
- Which formal/actual binding keeps the same signal connected after expansion?
- What source locations are verified, partial, shared, or unavailable?
- Which source hashes, concrete parameters, libraries, tools, and passes
  produced this snapshot?
- Does the current editor differ from the compiled source snapshot?

## Vocabulary and hierarchy

| Term | Contract |
| --- | --- |
| Source definition | A BSV declaration; not necessarily a hardware cell. |
| Elaborated occurrence | One instantiation in a particular parent/parameter context. |
| Implementation hierarchy | Actual containment retained by the chosen RTL/netlist. |
| Presentation region | A view-only group, never counted as a hardware cell. |
| Module / block / instance | A real definition or occurrence, clearly distinguished. |
| Port / signal / bus | An artifact pin or ordered set of signal/constant bits. |
| Register / memory / operator | A glyph justified by actual cell type semantics. |
| Unknown cell / black box | Known contract retained; unknown internals not fabricated. |

Primary UI does not expose Protocol Channel, Endpoint, `projectionFocusId`,
or legacy bucket counts. Methods, rules, interfaces, scheduling, and potential
source dependencies are explanations associated with selected hardware.

A source boundary that was inlined may be shown only from verified
correspondence and must say `logical/source boundary; inlined in implementation`.
Shared circuitry may have several source origins, but only one implementation
owner. Two independent roots remain independent inside a non-hardware workspace
container. Role classifications do not change parents or connect roots.

## Navigation and selection

- An expandable block body has one primary action: enter/expand.
- A distinct Info action inspects it without navigating.
- A port, net, leaf, or black-box action inspects and does not bubble to entry.
- Clicking the current expanded boundary selects it or does nothing.
- Background clears selection; dragging pans and must not trigger entry.
- Enter activates the primary action. Space inspects. Focus is visible.
- Double-click and repeated activation cannot enter two levels accidentally.
- Wheel zoom changes geometry, not containment or history.
- Back/Forward restore previous/next distinct scenes. Up navigates to the
  actual parent. Breadcrumb movement is a navigation transaction.
- Re-entering the identical destination/state is a no-op. Selection, hover,
  and each pan frame do not append history entries.
- Source/RTL inspection retains snapshot and occurrence context.

## Evidence and uncertainty

Details show artifact identity before interpretation. Each line can be traced
to ordered connection bits, each block to its module/cell pointer, and each
crossing to an explicit formal/actual boundary binding.

Original source may be direct, multiple-origin, transformed, shared,
optimized-away/merged (only with proof), or unmapped. The UI separates:

- artifact structure verified;
- original BSV evidence status;
- inferred semantic grouping;
- source/snapshot freshness.

No BSV column is invented when a provider only gives a line. Source evidence
must equal the referenced file slice at the recorded content hash. A stale
mapping opens compiled read-only source, not a shifted current line.

Unknown type, truly absent payload, composite interface legs, different
request/response payloads, unbound, unsupported, and not compiled are distinct.
Null is not `No payload`; missing dependency information is not `No dependencies`.
Missing source guard is not evidence of unconditional hardware eligibility.

## Fallback, execution, and security

`Compiled hardware` always names a successful immutable snapshot.
`Source-derived preview - compiled wiring unavailable` is a separate mode.
A missing compiler does not prevent importing a supported existing artifact.
Failed builds preserve the previous successful snapshot.

Production build execution belongs to the extension host/worker, behind
Workspace Trust and an explicit user action. The webview never runs a compiler,
reads arbitrary files, executes Tcl, or sends HDL to an external service.
Executable, argv, working directory, output location, and relevant build options
must be inspectable. No automatic build on save, hidden binary download,
arbitrary script-as-data import, or global profile/PATH mutation.

Readers enforce size, depth, object-count, path, symlink, and malformed-bit
limits. Source resolution uses approved roots and matching hashes. Labels and
source text are data, rendered with text nodes and a restrictive CSP.
The isolated G1 experiment is not proof of VS Code host trust integration.
